# Agent Note: Writer lock reclamation keeps a live org bundle authorized

Status: implemented

[English](2026-11-05-writer-lock-reclamation.md) | 中文

## 问题

桌面客户端启动后，内网模型 bundle 可能从模型列表中消失，且多次重启都不会自愈。上报的日志是 `atomic-write` 在等待写锁时超时，锁路径为 `C:\Users\<用户>\.dsh\profiles\desktop\package.json.lock`。

手工把这个锁文件改名后客户端即恢复，这是"孤儿锁"的典型特征，而不是写入缓慢。

两个彼此独立的缺陷叠加成了这一结果。

**锁永远无法被回收。** `withFileLock` 以 `wx` 创建 `<file>.lock`，并在 `finally` 中删除，但没有任何参与者检查锁内记录的持有者是否还在。锁文件本身已写入创建者的 PID，却从未被读取。本包曾刻意这样设计：*"竞争者绝不移除锁……恢复是操作者的动作。"* 因此，任何在持锁期间退出——进程被杀、崩溃，或释放操作本身因 Windows 瞬时句柄占用而失败——都会留下一个让该文件之后所有写入方永久失败的锁。释放逻辑还放大了这一点：`rm` 在同一个 `finally` 中执行，因此删除失败既会丢弃操作的返回值，又会把锁留在磁盘上。

**锁超时又被放大成了撤销授权。** 在 `managed-sync` 中，受管 bundle 的授权是进程内的，新进程中为空，因此首次 `loadProfileDirectory` 会跳过它。授权只能由轮询循环调用 `setBundleEnabled` 来恢复，而这需要同一把锁。插件循环的 `catch` 把任何失败都当作插件失败：记录 `Failed` 并调用 `disable`，而 `disable` 在尝试写入之前先调用 `authorizeManagedBundle(dir, name, false)`。于是一次锁超时，就撤销了一个磁盘上完好的插件的授权；又因为 `.aigc-plugin-state.json` 里仍登记着该包，每次启动都会重复这一过程。`disable()` 的写法同样有这个问题——先撤销授权、再尝试写入——因此那里的一次瞬时失败也可能下线一个正常工作的 bundle。

## 决策

- 用导出的 `WriterLockTimeoutError`（`code: 'LOCK_TIMEOUT'`）替代等待超时时的裸 `Error`，使"失败时会改动持久状态"的调用方能够区分竞争与对自身操作的判定。
- 竞争者只在锁内记录的 PID 可证明已不存在时才回收：该值须为正整数，且 `process.kill(pid, 0)` 返回 `ESRCH`。存活 PID、无法解析或为空的锁内容，以及其他任何探测错误，都会保留锁不动，因为抢走一个存活的锁会引入两个并发写入方。
- 回收绝不影响已经易主的锁。先把锁 rename 到别处，这样当前竞争者独占其捕获的那个 inode；随后复查被捕获的文件，若其持有者又变为存活，则将它 rename 回去。若连还原都失败，宁可留下该文件也不删除。
- 释放会短暂重试、吸收瞬时句柄占用，且从不抛错。这里的失败不能覆盖操作本身成功的结果，而遗留的锁会在持有者退出后由下一个竞争者回收。
- 在 `managed-sync` 中，`LOCK_TIMEOUT` 不再产生 `Failed` 上报、不再调用 `disable`、不再撤销授权。插件保持上一状态，下一次轮询重试，且使用比常规 `managedPollMs` 更短的 `managedLockRetryMs`（默认 5000 ms）。账户切换校验仍然执行，因为锁冲突不是跳过它的理由。
- `disable()` 记录调用前的授权与激活状态，并在写入失败时两者都恢复，因此一次失败的卸载无法撤销一个磁盘上仍启用的 bundle 的授权。
- 激活路径在 `setBundleEnabled` 拒绝时恢复先前的授权；外层轮询 `catch` 不再因锁冲突而调用 `disableAll`。

## 考虑过的替代方案

**删除任何超过固定时长的锁。** 存续时间无法区分已崩溃的持有者与仅仅被暂停的写入方，而一次长时间的 pnpm 操作合法地持有此锁数分钟。PID 是直接证据；定时器只是猜测，且会在危险方向上出错。

**依赖操作者手动删除锁。** 这正是已交付的行为，也是上报的故障：不能指望桌面用户自己找到 `~/.dsh/profiles/desktop/package.json.lock`。它也无法扩展——每台受影响的机器就是一张工单。

**通过 unlink 锁再重试独占创建来回收。** 单纯 `unlink` 没有顺序保证：上一个持有者可能在检查与 unlink 之间释放，从而删掉第三个写入方刚刚取得的锁。先 rename 到别处能把这一交互变成可观测的，而不是竞态的。

**把锁超时当作插件失败。** 正是这一点让瞬时状况变成了永久故障。竞争是关于 profile 写入方的证据，而不是关于 bundle 完整性的证据，因此正确反应是延后，而不是撤销授权。

**竞争时立即重试整个轮询。** 对一个被 pnpm 安装全程持有的锁做密集重试会空转。单独设置较短的延后既能及时恢复，又不与持有者争夺。

## 验证

| 证据 | 覆盖的行为 |
|---|---|
| [锁测试](../../../../packages/util/atomic-write/tests/atomic-write.spec.ts) | 回收持有者已退出的锁；存活持有者的锁与 PID 保持不动；持有者不可解析时保留原地；上报带路径的 `LOCK_TIMEOUT`；操作抛错后仍释放锁。 |
| [管理器测试](../../../../packages/boot/plugin-manager/tests/manager.spec.ts) | 策略版本变更期间 `setBundleEnabled` 遭遇竞争时，bundle 仍保持授权与加载，不上报 `Failed`，并在锁释放后恢复上报 `Active`。 |

回收测试写入的是一个真实已退出子进程的 PID，因为伪造的超范围 PID 在 Windows 上抛出的是 `ERR_INVALID_ARG_TYPE` 而非 `ESRCH`，无法命中预期的探测分支。管理器测试从激活路径注入 `WriterLockTimeoutError`；它正是修复前会失败的回归用例——可观察到 `marketProbe` 消失且 `isManagedBundleAuthorized` 变为 false。

## 后果

- 若锁内 PID 被无关进程复用，该锁会被视为存活并超时，这是安全的方向；该进程退出后文件即被回收。
- 在 `wx` 与写入 PID 之间死亡的写入方会留下内容为空的锁，任何竞争者都不会回收它。这个窗口只有几微秒，而"回收不可解析的锁"会从被暂停的持有者手中抢锁。
- `LOCK_TIMEOUT` 现已成为本包公开接口的一部分。此前按错误文本匹配的调用方可以改为匹配该 code。
- 因锁竞争而跳过的轮询不会向管控面上报，组织端在该区间看到的是上一次状态，而不是虚假失败。因此即便锁永久卡住，降级结果是状态陈旧加告警，而不是插件被撤销授权。
- 受影响机器上已存在的孤儿锁会在下一次写入尝试时自动恢复：无需支持介入，也无需手工改名文件。
