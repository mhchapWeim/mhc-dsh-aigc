# 模型图片理解能力修复

本次源码修改在 `main` 分支。用户于 2026-10-20 确认该分支为当前生产环境使用的分支。本文不是部署完成记录。

## 行为

模型管理增加“图片理解”：自动识别、支持图片、不支持图片。管理员的明确配置优先于上游声明；自动模式只采用 LiteLLM `/model/info` 对实际 `ModelIdentifier` 返回的布尔值。缺失、null、查询失败均为未知；同一别名的多个部署声明不一致也为未知。没有按显示名称、版本号或 Flash 后缀推断能力。

服务端保留旧 `input` 字段，并增加 `imageInput.state/source/reason`。未知状态的旧 `input` 为 `["text"]`，保证旧客户端不会擅自发送图片；新客户端在图片提交时显示“图片能力尚未确认”，文字对话仍可用。旧管理端未提供新字段时，保存不会清除已有覆盖配置。

内网模型目录和实际连接都返回能力。插件 1.0.7 删除仅文本硬编码，接入宿主附件服务，在每次授权后直连模型服务。图片使用既有 pi-ai 附件序列化，支持 base64 内容块；不会把 AIGC 登录令牌传给模型服务。未知模型在主会话、子代理和直接运行时调用中均拒绝图片，不能静默去掉图片后继续生成。

图片理解与图片生成独立，本次不增加生图接口。

## 发布顺序

1. 备份数据库与当前 API/Portal 镜像、DSH 安装器、插件发布版本和配置。检查生产实际状态。
2. 审查 `deploy/sql/20261020-model-image-input.sql`。只添加默认值为 Auto 的列，不更新模型能力、不更换标识或密钥。脚本列出模型总数、ID 唯一数、重复别名及三个模型的候选条目。部署前执行获批脚本；应用既有的加法 schema 初始化也包含同一列。
3. 构建并更新 API 和 Portal，再发布包含此次宿主和界面变更的 DSH 客户端。仅上传插件不能更新托管适配器、主会话预检和未知能力文案。
4. 上传并发布 `plugins/dsh-plugin-internal-model/bhss-dsh-plugin-internal-model-1.0.7.tgz`，保留原配置和授权，客户端同步后按提示重启 Host。兼容基线仍为 `0.1.7-alpha.2`。旧客户端的已明确支持能力可由新 API/插件传递，但未知状态的准确提示和运行时保护需要新 DSH。
5. 在模型管理中核对三个模型各自的真实部署。若上游已明确声明支持可保留自动模式；否则经接口核验后逐一设置“支持图片”。Local 接入没有自动的 LiteLLM 能力来源，需要管理员明确配置。不得给全部模型批量开启。
6. 用三个模型分别提交已知内容的截图和普通图片，核对请求包含 `image_url`、模型回答正确；使用纯文本模型和未知模型分别验证拒绝原因，回归文字、工具调用及授权撤销。

数据库脚本尚未在生产执行；本地测试只证明能力传递、拒绝与序列化，不代表实际模型服务已支持该请求。
